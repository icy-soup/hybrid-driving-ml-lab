# 交通仿真、车辆 AI 与 UI 重建规格

## 1. 目标

在保留当前机器学习实验链路的前提下，恢复并重构旧版项目中的交通仿真能力。新版主环境必须能够解释周围车辆为什么加速、减速、跟驰、变道或发生碰撞；UI 只负责渲染主环境状态，不再维护另一套独立运动逻辑。

本阶段不实现手动驾驶，也不训练强化学习模型。强化学习只要求保留清晰的环境和策略接口。

项目后续算法主线固定为：规则基线 → 行为克隆 → 短时域离散 MPC → GPU DQN → 行为克隆初始化 DQN → DQN 安全屏障。交通仿真和基线稳定后才进入 MPC 与强化学习阶段。

## 2. 参考与边界

实现依据按以下优先级排列：

1. 当前项目的稳定数据契约、奖励和评测接口；
2. 旧版 `legacy/pre_refactor/2_ai` 中的 UI、车辆资源和交通 AI；
3. 用户提供的 `同车行.../full.md` 中的车辆动力学、传感器区域、跟驰和变道原则。

旧版代码只作为行为参考，不能未经审核直接复制。远程 `main` 保持在 `368d02f`，所有实现先在本地完成和验收。

### 2.1 论文思想的落地范围

用户提供的 `full.md` 论文作为交通建模参考，采用其中“共享动力学、分离控制策略”的原则：

- 自车控制器参考论文的有限状态机思想，保留巡航、跟驰、左变道、右变道和变道暂停等可解释模式；
- 自车的实际实验策略仍由 `RulePolicy`、`NeuralPolicy` 和 `HybridPolicy` 提供，论文 FSM 不替代机器学习基线；
- 交通车使用独立的驾驶者模型，参考论文中的跟驰、期望速度、时间间隔和安全变道窗口；
- 交通车通过 conservative、normal、aggressive 参数体现不同驾驶风格，不复用自车策略网络；
- 论文中的前中、前左、前右、后左、后右传感器区域用于统一观察接口设计；
- 论文中的连续纵向/横向运动和变道时间用于车辆动力学验收；
- 论文中的距离、安全违规、控制努力和舒适性思想用于扩展评测指标，但不直接声称复现论文实验结果。

论文只提供模型设计参考，不作为当前项目的实验数据来源，也不要求复制其博弈论交通模拟器。

## 3. 统一仿真状态

每辆车必须包含以下状态：

- `vehicle_id`：稳定标识；
- `x`：纵向位置；
- `y` 或连续横向车道位置；
- `lane` 与 `target_lane`；
- `speed`、`desired_speed`、`acceleration`；
- `length`、`width`；
- `behavior_mode`；
- `is_changing_lane`、`is_crashed`。

自车和交通车使用同一套坐标、单位和时间步。车辆不会通过瞬移完成变道，变道必须有明确持续时间和横向轨迹。

## 4. 交通更新顺序

每个仿真步固定执行：

```text
感知 → 行为决策 → 纵向控制 → 横向控制 → 状态积分 → 碰撞检测 → 事件记录
```

交通车行为模式至少包括：

- `CRUISE`；
- `FOLLOW`；
- `BRAKE`；
- `PREPARE_LANE_CHANGE`；
- `LANE_CHANGE`；
- `LANE_CHANGE_ABORT`；
- `EMERGENCY_BRAKE`；
- `CRASHED`。

交通车需要支持期望速度、速度边界、加速度边界、跟驰距离、TTC 和相邻车道安全检查。驾驶风格通过参数配置区分 conservative、normal、aggressive，不复制三套逻辑。

## 5. 感知与碰撞

感知必须基于车辆几何范围和车道重叠，而不是只比较 sprite 左边缘。至少输出前中、前左、前右、后左、后右车辆的距离、相对速度、TTC 和占用状态。

碰撞检测需要区分：

- `ego_traffic`：自车与交通车；
- `traffic_traffic`：交通车之间；
- `rear_end`：纵向追尾；
- `side`：变道或横向碰撞；
- `obstacle`：与静态障碍物碰撞。

碰撞事件必须包含双方 ID、时间步、场景、车道、碰撞前间距、碰撞后间距、双方速度、TTC、行为模式和原因。

## 6. 诊断输出

每个 episode 支持输出逐步 JSONL 轨迹和最终汇总。逐步记录至少包含：

- 自车状态与动作；
- 所有交通车状态；
- 各车辆行为模式；
- 当前感知结果；
- 奖励分量；
- 碰撞、变道、超车和安全接管事件。

最终汇总包含碰撞次数、碰撞类型分布、碰撞原因分布、最大/最小 TTC、变道次数、超车次数、平均速度、存活步数和回报。

## 7. 策略接口

保持：

```python
policy.act(observation) -> Action
```

Rule、Neural、Hybrid 继续实现该接口。环境观察扩展后，现有策略通过适配层兼容；新算法不直接依赖 Pygame。

## 8. UI 重建

UI 迁移旧版布局和资源，但只读取当前环境状态。UI 必须显示：

- 三车道道路和车辆动画；
- 自车策略与动作；
- 每辆附近交通车的行为模式；
- 速度、车道、TTC、安全距离；
- 当前 episode 指标；
- 最近事件和碰撞原因。

UI 不实现独立的交通运动，不复制 `HighwayEnv` 的更新逻辑。Pygame 是可选展示层，不影响无界面训练和测试。

## 9. 测试验收

必须增加并通过：

- 车辆初始不重叠；
- 跟驰车辆不会穿透前车；
- 变道过程连续且可完成/中止；
- 交通车碰撞可检测并解释；
- 自车碰撞可检测并解释；
- 固定 seed 轨迹可复现；
- UI 与无 UI 使用同一环境状态；
- 原有数据、训练、评测和向量环境测试全部回归通过。

完成后先在本地运行完整验收和 UI 演示，由用户确认，再合并阶段性提交并同步 GitHub。

## 10. MPC 与强化学习扩展

### 10.1 MPC

加入一个与其他策略兼容的 `MPCPolicy`。第一版采用短时域离散滚动预测：枚举未来 3-8 步的离散动作序列，用当前环境动力学预测碰撞风险、速度跟踪、进度、变道代价和控制努力，只执行最优序列的第一步。

MPC 使用与自车策略相同的观察和动作接口，不参与交通车行为模型，也不依赖 Pygame。没有连续动力学和诊断输出之前，不宣称实现完整车辆级连续 MPC。

### 10.2 强化学习

强化学习策略不是人工规则，而是根据奖励学习的策略。第一版使用 GPU 可用的 DQN，保留 CPU smoke run；动作空间沿用现有 5 个离散动作，观察空间沿用扩展后的环境观察。

至少比较：

- `DQN-random-init`；
- `DQN-BC-init`；
- `DQN-BC-init + safety shield`。

强化学习只训练自车。交通车使用独立的规则驾驶者模型和驾驶风格参数。安全屏障可以使用规则策略覆盖危险动作，但必须记录覆盖次数和效率代价。
